# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Bakers is a French bakery companion app: a recipe library, technical tips, an AI baking assistant, and community features (likes, comments, friends, messaging). It's a two-part monorepo:

- `backend/` — FastAPI + MongoDB (Motor), a single-file API server
- `frontend/` — Expo Router (React Native + TypeScript), targets iOS/Android/Web

The project previously ran on "Emergent" (an AI app-builder platform) for auth, file storage, and the AI provider. That coupling has been removed: auth is email/password only, file storage is local disk, and the AI assistant calls the Anthropic API directly. A few harmless traces of the old scaffold remain (see Gotchas below) — don't be alarmed by them.

## Commands

```bash
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env        # then fill in JWT_SECRET / ANTHROPIC_API_KEY / MONGO_URL
```

Needs a running MongoDB (`docker run -d -p 27017:27017 mongo:7`, or Atlas).

Most tests are **HTTP integration tests**, not unit tests — they hit a live server over the network (default `http://localhost:8000`, override via `EXPO_PUBLIC_BACKEND_URL`). The exceptions are `test_production_calc.py`, `test_staff_calc.py`, `test_seed_quality.py`, `test_moderation_calc.py`, `test_imaging_calc.py` and `test_instagram_calc.py`, which are pure and need no server. Start `uvicorn` first, then:

The graduated-classification tests in `test_messaging_photos.py::TestGraduatedLevels` additionally need the server under test started with `MODERATION_PROVIDER=stub` (see "Message photos" below) — they skip themselves otherwise rather than failing, since a real Sightengine response to a solid-colour test image isn't predictable.

```bash
cd backend && pytest                        # runs the full suite (all files in tests/)
pytest tests/test_bakers_api.py             # single file
```

## Architecture

### Backend — `backend/server.py`

Everything (models, auth, all routes, startup seeding) lives in this one ~600-line file behind an `/api` prefix router. Key pieces:

- **Auth**: hand-rolled JWT (HMAC-SHA256 over base64url header/payload, `sign_jwt`/`verify_jwt`), not a third-party library. `get_current_user` is the single dependency every protected route uses. Passwords are bcrypt-hashed. There is no token revocation — logout is client-side only (stateless JWT).
- **Storage**: `put_object`/`get_object` in the "Storage Helpers" section write/read files under `backend/uploads/`, keyed by an app-generated path (`bakers-app/uploads/{user_id}/{uuid}.{ext}`). `_resolve_upload_path` guards against path traversal on the `/api/files/{path:path}` download route — keep that guard if you touch storage. `put_private_object`/`get_private_object` are the same shape but rooted at a *different* directory (`backend/private_uploads/`) that `/api/files/{path:path}` cannot reach at all — used for message photos, which are never served through the public route (see "Message photos").
- **AI chat**: `/api/chat` calls the Anthropic API directly (`anthropic.AsyncAnthropic`, model `claude-sonnet-5`). It's stateless per-request — conversation history is reconstructed on every call by reading recent `db.chat_messages` for the `(user_id, session_id)` pair and replaying them as the `messages` array. Returns 503 if `ANTHROPIC_API_KEY` isn't set.
- **Data model**: MongoDB, no ORM, plain dicts. Collections: `users`, `recipes`, `favorites`, `likes`, `comments`, `notes`, `friendships`, `friend_requests`, `messages`, `reports`, `chat_messages`, `tips`, `productions`, `schedules`. Indexes are created in the `startup` handler, which also **syncs** recipes and tips from `seed_data.py` on every boot (upsert keyed on the title, so a fix reaches the DB on the next deploy). Community-submitted recipes are never touched. A `messages` doc has `type: "text"|"photo"`; a photo message additionally carries `photo_path`, `photo_blur_path` (only when `sensitive`) and a `moderation` dict — see "Message photos".
- Recipes carry a computed `like_count` / `coup_de_coeur` (top-5-liked badge) via `enrich_recipes`, applied after every recipe fetch.
- Friends/messaging require an accepted friendship (`_are_friends`) before messages can be exchanged; friend pairs are stored as a sorted 2-element array so either ordering matches.

### Recipe families — `backend/families.py`, `frontend/src/families.ts`

The catalogue is browsed by **family** (Pains, Tartes, Biscuits et sablés…), a rank between the three categories and the sheet: eighty recipes under "Pâtisseries" could not be read as one list. `backend/families.py` is the single source — an ordered `FAMILIES` list and a `FAMILY_BY_TITLE` table covering every seeded recipe. `seed_data.py` stamps `family` on each recipe at join time and **refuses to import** if a title is missing from the table, since a recipe no tile opens is a recipe nobody finds.

- A family belongs to exactly one category, which is why base doughs are split into `pates-tourees` (Viennoiseries) and `pates-a-tarte` (Pâtisseries) instead of one straddling family.
- `pains` is currently **declared but empty**: the imported work is a pastry and viennoiserie book. Empty families are not returned by the API and the browse chips are derived from the families actually present, so both the tile and the "Pains" chip reappear on their own with the first bread.
- Three `catch_all` families (`autres-*`) exist only for community recipes submitted without one. `GET /api/families` omits empty families, so they stay out of the grid until something lands in them; `?include_empty=1` is for the share form, which has to offer a family before anything is in it.
- Tiles are **drawn, not photographed**: `frontend/assets/images/families/*.svg` rendered to PNG by `frontend/scripts/build-tiles.mjs` (Chromium via Playwright, run by hand, not part of the build; it renders the `products/` tiles too). Only `src/theme.ts` colours are used. `FAMILY_TILES` in `src/families.ts` is a `Record<FamilyKey, …>`, so a family without a tile fails `tsc` rather than showing an empty box.
- Recipe cards inside a family carry **no image** on purpose: the imported sheets have no photo, and one generic picture repeated over nineteen tarts would read as a photo of each. (The recipe *screen* does carry a drawn illustration — see the next section for why a drawing is allowed to repeat where a photo isn't.)

### Recipe images — `backend/recipe_photos.py`, `backend/products.py`, `frontend/src/products.ts`

None of the 194 imported sheets carries a photo of its own: the books' photographs are not reproduced (the data is taken, the images are not). Images therefore come from outside, and one function decides which — `recipeImage(recipe, apiBase)` in `src/products.ts`, used by the recipe screen, the home screen, the profile and the baker page so they cannot diverge. Four steps, in order:

1. the **upload** of a community recipe (`image_path`);
2. a **photograph of the product**, when one exists that really shows *that* product (`image_url`, from `recipe_photos.py`);
3. the **drawing of its archetype** — the shape, not the dish (`products.py`);
4. nothing, and the screen paints a plain warm band (never a grey one, which reads as a failed image load).

A drawing reads as an **emblem** rather than as a picture of that particular piece, which is exactly what makes repetition acceptable where a photo would lie: nineteen tarts sharing one drawing say "a tart"; nineteen copies of one photo would say "here is *that* tart". A photograph earns its place only by being of the right product — which is why step 2 sits above step 3 but is much harder to fill.

#### Photographs — `backend/recipe_photos.py`

Photos come from **Pexels** (Pexels License, commercial use, no royalty). Wikimedia Commons was tried first and abandoned: it is a documentary archive, not a culinary photo library — a "croissant" search returned an *oranais*, a "bretzel" search a branded sandwich on a cafeteria tray. Both had a perfect title.

That failure is the whole design of this table:

- **A photo is never chosen on its title.** It is *looked at*. Every entry carries a `vu` field recording, in French, what was actually seen in the image; `tests/test_recipe_photos.py` rejects an entry without it. `tools/harvest_pexels.py` exists to make that review possible at scale — it queries Pexels and builds one **contact sheet** of candidates per recipe, and deliberately chooses nothing itself.
- **Nothing rather than roughly right.** A recipe whose product has no honest photo gets none and keeps its drawing. The table does not cover the whole catalogue, and that is deliberate.
- **The credit is not optional.** Pexels' *API Guidelines* go further than the licence and require naming the photographer with a link to their profile plus a link back to Pexels. That is what `image_credit` renders under the photo, in the style of the existing "D'après …". An entry with no author or no source page is rejected by the tests: you cannot credit what you did not record.
- `url` points at the Pexels CDN, which permits hotlinking; nothing is copied into the repo. The search happens once, at harvest time — the app never talks to Pexels.
- Harvesting needs `PEXELS_API_KEY` **and** `api.pexels.com` / `images.pexels.com` allowed by the environment's network policy. Without both, the table stays empty and every sheet keeps its drawing, which is a valid state rather than a failure.

- `backend/products.py` is the single source, same shape as `families.py`: an ordered `PRODUCTS` list of archetype keys and an `_ASSIGNMENTS` table mapping recipe titles to them. `seed_data.py` stamps `product` on each seeded recipe via `product_of`.
- Unlike `family`, `product` is **allowed to be absent**, and the table deliberately does not cover the whole catalogue (150/194). A kouglof, a braid or a palmier gets no archetype because no drawing renders that shape honestly — a pain de mie illustrated by a boule would be worse than nothing. `app/recipe/[id].tsx` then shows a plain warm band (not a grey one, which would read as a failed image load).
- Tiles come from the same pipeline as the family tiles: SVG in `frontend/assets/images/{families,products}/`, rendered to PNG by `frontend/scripts/build-tiles.mjs` (now walks both directories). Sixteen archetypes reuse a family tile that already draws exactly that shape; six are drawn for the products. Only `src/theme.ts` colours are used.
- `PRODUCT_TILES` in `src/products.ts` is a `Record<ProductKey, …>`, so an archetype without a tile fails `tsc`. `backend/tests/test_products.py` covers what `tsc` can't see: an unknown title, an archetype nobody uses, a `require` pointing at a missing PNG, a PNG with no SVG source.
- The short list of archetypes is the point, not a to-do: drawings that didn't read (a spiral overflowing its frame, a braid that looked like a chain of beads) were thrown away rather than shipped.
- There is **no hardcoded remote image left in the app**. Six render sites used to fall back to a single Unsplash URL (`photo-1509440159596-…`, a scaffold leftover of unverified licence) or to nothing at all — the home hero and its "Grands classiques" cards rendered empty white boxes for all 194 recipes. They all go through `recipeImage` now. If you add a screen that shows a recipe, use it rather than reaching for `image_url` directly.

### Recipe content — `backend/seed_data.py`, `backend/seed_books.py`

**Every recipe now comes from `seed_books.py`** — sheets taken from professional works, each carrying the page it was read from. The twenty demonstration recipes the app was scaffolded with have been removed: they were written by a language model, not a baker, and a recipe that cannot say where a quantity comes from has no place in a bakery tool. The eight original tips are the last of that batch and are still there, unsourced.

Two works are imported so far, and `source` names which one each sheet came from:

- **Josée Fiset, « Comme à la boulangerie », Pratico Édition** — 90 sheets, the home-baking pastry catalogue. Read from a PDF with a text layer, so it went through an extraction pipeline whose faults `test_seed_quality.py` was written against.
- **FERRANDI Paris, « Boulangerie Viennoiserie », Flammarion** — 104 sheets: the breads, the preferments, the base doughs, the viennoiserie and the filled breads. The PDF is a **scan with no text layer**, so its pages were read directly rather than OCR'd: an OCR turning an 8 into a 3 announces nothing, and a wrong quantity is the only really serious fault in a bakery tool.

**One sheet per product.** Where both books cover the same thing — croissant, pain au chocolat, babka, tarte au sucre, pâte à brioche… — the FERRANDI version replaces the Québec one, which leaves the seed and is deleted from the database by `retire_built_ins` on the next deploy. That is what keeps FERRANDI's chain of cross-references honest: its croissant leans on *its* pâte levée feuilletée, with its own quantities. The replaced titles are listed in the generator, not hidden in a diff.

**The seed is authoritative in both directions.** The startup handler upserts every recipe in `RECIPES_SEED` *and* deletes built-in recipes that are no longer in it (`retire_built_ins` in `server.py`, covered by `tests/test_retire_seed.py`). Retiring content is therefore a deploy, not a manual database cleanup. Two rules keep that safe: only `is_user_submitted: False` documents are ever considered, and the likes/comments/notes/favourites of a deleted recipe go with it. A production already built on a deleted recipe keeps working — it snapshots ingredients and steps — but *editing* it will 404 on the missing recipe.

- `seed_books.py` is **generated then reviewed**, not hand-maintained line by line. Quantities, temperatures, durations and yields are copied from the cited work; descriptions and step lists are written for Baker. Method paragraphs are deliberately **not** reproduced — the data is taken, the prose is not. That distinction is what makes the import legitimate in a distributed app, so keep it if you add a source.
- Two optional fields carry the import: `technical` (a dict — the keys the recipe screen knows how to render are listed in `TECHNICAL_ROWS` in `app/recipe/[id].tsx`; an unknown key is silently invisible) and `source` (the work and page). Absent means "not stated in the source", never an estimate.
- `hydration` is filled only when the water-and-milk over flour ratio is directly computable — preferment included, since its own flour and water are given; it stays 0 otherwise rather than being guessed. It also stays 0 when the figure would be *arithmetically* right but misleading: water drunk by a seed soaker, by cocoa powder, or a dough whose liquid is beer.
- Where a book contradicts itself — a sidebar saying 20 minutes and the method paragraph saying 35 — the **method paragraph wins**, because the sheet has to agree with itself on screen. These are listed in the import notes, not silently averaged.
- `tests/test_seed_quality.py` is the guardrail: it runs without a server and checks the whole catalogue for the faults a PDF extraction actually produces — sentence fragments in ingredient lists, unbalanced parentheses, leftover imperial measures, book cross-references ("photo B"), implausible temperatures, a `yield_pieces` that contradicts its own label. Run it before touching seed content.

### Recipe scanning — `backend/scan.py`, `frontend/app/scan.tsx`

A user can photograph a paper recipe sheet (camera or photo library, one or several pages) and turn it into a recipe. This deliberately does **not** create a second recipe system: the scan screen's "Ajouter à mes recettes" button builds the exact same payload `share.tsx` already builds and posts it to the same `POST /recipes` — same text moderation, same family fallback, same cover-photo upload via `POST /upload`. There is no recipe-edit endpoint anywhere in the app, so the verification screen is the only chance to get every field right before it's permanent.

- **Extraction, not a second AI service.** `POST /recipes/scan/analyze` reuses the same `anthropic_client` as `/api/chat` (model `claude-sonnet-5`) — Claude's vision capability reads the photographed page directly, no separate OCR provider. It's the first use of Anthropic tool-use (`tools=`/`tool_choice`) in this codebase, deliberately: a JSON schema (`SCAN_TOOL`) guarantees structured, valid output instead of parsing free text, for a response this shaped (confidence-tagged ingredients, steps, fabrication fields).
- **Never invents.** The system prompt and tool schema require a `confidence: "high"|"low"|"absent"` on every extracted field; `"absent"` means the field is left `null`, never a guess. The frontend shows a ⚠️/"non détecté" badge next to any field that isn't `"high"`, and nothing is pre-filled with invented content — an empty required field (title, description, at least one ingredient, at least one step, the total duration) blocks submission exactly like `share.tsx` already does for a missing field.
- **Nothing is stored server-side beyond the request.** Each page is resized/contrast-enhanced by `imaging.prepare_for_analysis()` (higher resolution and a lighter JPEG compression than `prepare_display()`, since legibility matters more than display size here), base64-encoded, and sent to Claude — never written to `uploads/`, never passed through `put_object`. `POST /recipes/scan/analyze` inserts nothing into the database; only the final `POST /recipes` call does, once the user is satisfied.
- **No perspective correction or edge detection.** The app has no document-scanner library and adding one would be a new native dependency; the existing `expo-image-picker` crop UI (`allowsEditing: true`, already used by `share.tsx`) is reused instead, and Claude Vision reads a moderately imperfect photo well enough not to need one. Camera capture itself needed no new dependency either — `expo-image-picker` already bundles `launchCameraAsync`, just never called anywhere before this feature.
- **Baker's percentages and hydration are computed, never trusted from the sheet.** `backend/scan.py` (pure, same family as `production.py`) sums every ingredient whose name contains "farine" as the 100% reference, and — for hydration — only ingredients named exactly "eau" (or "eau froide/tiède/glacée/chaude"), never a substring match ("eau de fleur d'oranger" doesn't count) and never another liquid (milk, melted butter). No flour or no water identifiable → `None`/`0`, the same "stay silent rather than guess" rule `seed_books.py` already uses for `hydration`. The frontend mirrors this exact logic locally (`computeBakerStats` in `scan.tsx`) so it recomputes live as the user edits an ingredient, without a network round-trip per keystroke.
- **`technical` gained four keys** (`room_temp`, `levure`, `observations`, `conseils`) in `TECHNICAL_ROWS` (`app/recipe/[id].tsx`) so a scanned recipe's fabrication details can actually be displayed — additive and backward-compatible, an existing recipe simply never sets them. A scanned recipe is tagged internally via `technical.imported_via = "scan"`, a key deliberately absent from `TECHNICAL_ROWS` so it's silently never rendered, the same "unknown key stays invisible" behaviour already relied on elsewhere.
- No scan quota exists yet — unlimited per authenticated user, same as `/api/chat` today; add one under `plans.py`'s `PLAN_LIMITS` if usage cost ever justifies it.

### Profile pictures — `frontend/src/avatar.ts`, `POST/DELETE /auth/me/picture`

Every user document has always carried a `picture` field (`db.users`, stamped `None` at registration) and every avatar-capable screen (`profile.tsx`, `friends.tsx`, `baker/[id].tsx`) already had the `picture ? <Image> : <initial>` conditional wired against it — a leftover of the removed "Emergent" OAuth scaffold, never reactivated since the app moved to email/password auth. This feature is that field finally getting written to, not a second profile system.

- **One conversion point.** `picture` is a raw storage path returned by the API (like a recipe's `image_path`), never a ready-to-use URL — `avatarUrl(picture, apiBase)` in `src/avatar.ts` is the only place that builds the displayable URL (`${apiBase}/files/${picture}`), mirroring `recipeImage()`/`recipeImageSource()` in `products.ts`. Every avatar render site calls it rather than using `{ uri: user.picture }` directly (what the dead code did, since it was written for a value that was never actually a path).
- **Never a stale copy.** Comments used to snapshot `user_picture` onto the comment document at creation time; `add_comment`'s document still carries it for backward compatibility, but `GET /recipes/{id}/comments` now overwrites it with a live lookup (`_pictures_by_user_id()`, one batched `db.users.find({user_id: {$in: [...]}})` for the whole page, not one query per comment). `enrich_recipes()` does the same for `author_picture` on every recipe list/detail response — never stored on the recipe document itself. Change your photo once, every comment and recipe you've ever posted shows it immediately, because nothing about your identity is ever copied onto content you created.
- **Square guaranteed server-side, not just client-side.** `share.tsx`'s cover-photo picker relies on `expo-image-picker`'s native crop UI (`allowsEditing`/`aspect`) — which `react-native-web` silently ignores, so a photo picked from a browser is never actually cropped. `imaging.prepare_avatar()` center-crops to a square unconditionally before resizing/compressing (`AVATAR_MAX_DIM = 512`), so every avatar is square regardless of platform, with the client crop as a nicety for native users to control the framing rather than the only thing making it square.
- **Same moderation, adapted policy.** Reuses `moderation.analyze()` (Sightengine) exactly as message photos do, but only `BLOCKED` is refused — `SENSITIVE` is accepted, since a profile picture has no blur/reveal mechanic to make an ambiguous result meaningful, and refusing it would just be blocking ordinary photos of people for no benefit.
- **Cache invalidation is automatic, by construction.** Every upload gets a fresh `uuid4().hex` filename (same pattern as `/upload`), so a new avatar is always a new URL — `expo-image`'s default URL-keyed cache never needs manual invalidation, and the old file is deleted (`delete_object()`, the first thing in this codebase that ever removes a stored object) so replacing a photo doesn't accumulate orphaned files.
- `ActionSheet` (`src/ActionSheet.tsx`) is a small reusable cross-platform bottom-sheet menu, extracted from the "scanner/créer manuellement" menu on the recipes screen once the avatar's "camera/library/delete" menu needed the same thing — `Alert.alert` is a no-op on `react-native-web` (see `src/confirm.ts`), so this is the only way to get a multi-option menu that works on web too.
- `useAuth().refreshUser()` re-fetches `/auth/me` and replaces the whole `user` object rather than patching `picture` locally — one source of truth (the server), reused by both the upload and delete flows.

### Profile bio + Instagram — `backend/instagram.py`, `frontend/src/instagram.ts`, `PUT /auth/me`

Two new fields on `db.users` — `bio` and `instagram_username` — join a profile that was already fully public (`GET /users/{id}/profile` has never checked any visibility setting; none exists in this app). `PUT /auth/me` is the first endpoint that can ever change anything about a user besides the picture, and follows the exact same ownership pattern: no target-user parameter, identity comes only from the JWT.

- **The username is stored, never the URL.** `backend/instagram.py`'s `parse_instagram_username()` accepts a bare handle, an `@handle`, or a full `instagram.com`/`www.instagram.com` URL (with or without scheme, `www.`, trailing slash, or query string) and extracts just the handle — any other domain is rejected before anything is parsed further. `instagram_profile_url()` rebuilds the link only at display time. `frontend/src/instagram.ts` is a line-for-line mirror of the same two functions; the two files change together or not at all.
- **Bio moderation reuses `text_moderation.classify_comment()` as-is** — it was already a generic freeform-text classifier (a one-line wrapper over `classify_text`), so a bio needed zero new moderation code: same `BAN_WORDS`/whitelist rules, same `_moderate_and_flag()` call (`content_type="bio"`), same BLOCKED-rejects/REVIEW-logs-and-publishes behaviour as a comment.
- **No HTML sanitization was added, deliberately.** React Native renders every string as plain text (`<Text>`) on both native and web — there is no `dangerouslySetInnerHTML` anywhere in this app — so a bio can never be interpreted as markup regardless of its contents. The 300-character limit is enforced both client-side (`maxLength`, the first use of that prop in this app) and server-side (`BIO_MAX_LENGTH`), since a client limit alone is never trusted.
- **`PUT /auth/me` treats an empty string as "clear this field"** (converted to `None` before storage) rather than adding a separate delete endpoint — the same request shape handles create/update/delete for both bio and Instagram.
- **Display, not linkification.** The bio is shown as inert text — never scanned for URLs or turned into tappable links — so there is no "hidden link" surface to defend against. The Instagram row is the only tappable element, and only because its value already passed the domain-restricted parser.
- **Opening Instagram is one plain `https://www.instagram.com/...` link, not a custom scheme.** A first version tried `instagram://user?username=...` behind `Linking.canOpenURL()` — Instagram dropped that scheme years ago (its exact shape is no longer guaranteed), and `canOpenURL` fails closed anyway unless `instagram` is declared in iOS's `LSApplicationQueriesSchemes`, which nothing here does — so it always fell through to opening a link that never actually left the app, reported as Instagram opening "inside Bakers." Fixed by dropping the scheme entirely: `openInstagram()` just opens the `https://` profile URL, and lets iOS/Android's own Universal Links / App Links hand off to the Instagram app when it's installed — no scheme, no permission, no `canOpenURL` check to get wrong.
- Both `frontend/app/(tabs)/profile.tsx` (own profile, inline edit form — this screen has never had a sub-screen navigation pattern, so editing stays inline next to the existing avatar-edit links rather than opening a new route) and `frontend/app/baker/[id].tsx` (public profile) render the same bio/Instagram block from the same `_public_user()` payload; nothing is rendered when both fields are empty.

### Creations gallery ("Mes créations") — `backend/server.py`'s Creations section, `frontend/app/creation/`, `frontend/app/creations/[userId].tsx`

A profile section where a baker shows off finished pieces (photo, name, description, optional category, optional link to one of their own recipes) — independent of the recipe library, since publishing a photo has never required publishing a recipe and the spec is explicit that it must stay that way. Built entirely by extending existing systems rather than adding parallel ones.

- **`db.creations`** is its own collection (`{user_id, user_name, title, description, category, recipe_id, photos: [...], created_at, updated_at}`), not a variant of `db.recipes` — a creation has no ingredients/steps/yield and forcing it into the recipe shape would mean nullable fields everywhere for a document that only sometimes looks like a recipe. `user_name` is denormalized (safe: no rename feature exists anywhere in this app); `user_picture` is never stored, always a live lookup via the existing `_pictures_by_user_id()` batch helper — same rule as recipe `author_picture` and comment `user_picture`.
- **Likes reuse the exact shape of `db.likes`, not a generic likes table.** The codebase already had two independent like collections following an identical pattern (`likes` for recipes, `comment_likes` for comments) before this feature — `db.creation_likes` (`{user_id, creation_id, created_at}`, unique compound index + a plain `creation_id` index, same toggle-and-absorb-`DuplicateKeyError` logic) is a third instance of that established pattern, not a new mechanism.
- **`POST /upload` was hardened, not duplicated.** It was, before this feature, the only image-accepting endpoint in the app with no size limit, no `imaging.py` processing, and no moderation call — used until now solely by `share.tsx` for a recipe's cover photo, with zero test coverage. Building a second upload endpoint for creation photos would have been exactly the "parallel system" this feature is supposed to avoid, so `/upload` itself now enforces `MAX_PHOTO_UPLOAD_BYTES`, runs every image through `imaging.prepare_display()`, and calls `moderation.analyze()` under the **avatar policy** (only `BLOCKED` is rejected — a photo of bread, pastry, or a person mid-bake is never blocked on mere ambiguity, and there's no blur/reveal mechanic here for `SENSITIVE` to plug into). The response shape (`{"path": ...}`) is unchanged, so the recipe cover-photo flow in `share.tsx` needed no changes and keeps working — it simply gets the same size/format/moderation guarantee for free now.
- **`CREATION_CATEGORIES` is a new, separate constant** (`["Pain", "Viennoiserie", "Pâtisserie", "Traiteur", "Autre"]`), deliberately not `families.CATEGORIES`: the recipe category list has no "Traiteur," and forcing creations onto that taxonomy would silently drop a category the spec explicitly asks for. `families.FAMILIES` is untouched.
- **Ownership is enforced server-side, not just hidden client-side.** `PUT`/`DELETE /creations/{id}` check `creation["user_id"] != user["user_id"]` → 403, the same guard already used for comment edit/delete — a user can never modify or remove another user's creation by calling the API directly.
- **Editing a creation's photo list deletes the dropped files.** `PUT /creations/{id}` diffs the old and new `photos` arrays and calls `delete_object()` on every path that fell out, the same "no orphaned files" principle already applied when an avatar is replaced. `DELETE /creations/{id}` removes every photo file, the creation document, and cascades `db.creation_likes.delete_many(...)`.
- **A dangling `recipe_id` never breaks the creation.** `GET /creations/{id}` resolves `recipe_id` into a `{id, title}` stub only if that recipe still exists at read time; otherwise the key is simply absent from the response and the creation is unaffected. In practice nothing in the app can delete a recipe a creation might reference except the seed-retirement cleanup at startup (`retire_built_ins`, and only on `is_user_submitted: False` docs) — but the check costs nothing and matches the spec's "never leave a broken link" requirement regardless.
- **No comments on creations.** The comment system is tied to `recipe_id` today and genericizing it wasn't asked for; a creation document carries no comment-related field, so nothing has to be redesigned if a `creation_comments` collection following the same shape gets added later.
- **No new schema for a future activity feed.** `creations.created_at` alongside the existing `recipes.created_at` is already enough for a future feed query merging both collections by date — nothing else was built toward that, per the explicit instruction not to build the feed now.
- **Gallery caps at 6 inline, with a dedicated overflow screen.** `profile.tsx`'s header block (where this section lives, next to the bio/Instagram block) is a sibling of the tab content `FlatList`, not itself scrollable, so an unbounded grid would run off-screen for a prolific baker. The inline section on both `profile.tsx` (own profile) and `baker/[id].tsx` (public profile) shows only the 6 most recent creations; past 6, a "Voir tout (N)" link opens `frontend/app/creations/[userId].tsx`, a plain 3-column `FlatList` with no cap. A public profile with zero creations renders the section not at all — never an empty block — while one's own profile always shows the section, with an "+ Ajouter une création" empty state when there are none yet.
- `frontend/app/creation/new.tsx` handles both create and edit (`isEdit = !!id`, same convention as `production/new.tsx`), including a searchable recipe picker copied from that same screen's existing "attach a recipe" pattern, and multi-photo selection via `expo-image-picker`'s `allowsMultipleSelection` (never used elsewhere in this app before now) for the library path; camera capture stays one-at-a-time, mirroring `scan.tsx`'s existing multi-page pattern.

### Comment replies and history — `PUT/GET` on `backend/server.py`'s comment routes, `GET /comments/mine`

Comments already supported one level of nesting (`parent_id`) before this feature — a reply always pointed at a root comment, never at another reply, and `GET /recipes/{id}/comments` already enriched every comment with a live `like_count` and the author's current picture. What was missing was a way to reply *to a reply* while still saying who it addresses, a way to edit a comment, and a history screen — this feature is those three additions, not a second comment system.

- **Reply-to-a-reply stays flat on purpose.** The depth stays at two levels — replying to a reply still sets `parent_id` to the *root's* id (so the existing cascade-delete and existing flat rendering loop `roots`/`repliesFor` never had to change), but the request also carries `reply_to_user_id`, resolved once server-side into a denormalized `reply_to_user_name` (safe to snapshot: no rename feature exists anywhere in this app, unlike a picture, which stays a live lookup precisely because it *can* change). The frontend only renders the "↳ Réponse à X" label when that name differs from the root comment's author — replying directly to the root needs no label, the indentation already says it.
- **`PUT /recipes/{recipe_id}/comments/{comment_id}`** is the first edit endpoint any comment ever had. Author-only (same `403` check as delete), and re-runs the *exact* same `text_moderation.classify_comment` an edit could otherwise dodge — a comment can't be published innocuous and then edited into something `create_recipe`/`add_comment` would have blocked.
- **`GET /comments/mine`** is cursor-paginated (`before` + `has_more`) rather than offset-based, deliberately copying `GET /messages/{friend_id}` — the only pagination convention this codebase has, not a second one invented for this screen. It batches the recipe lookups and `_comment_like_counts()` for the whole page in two queries total, never one per comment.
- **No notification system was built.** None exists anywhere in this app (`expo-notifications` is local baking timers only, unrelated) — `reply_to_user_id` is captured so a future notification feature knows who to notify, but nothing fires today.
- **Collapse/expand and "modifié" are display-only.** Replies beyond the first two collapse behind "Voir les N réponses" (local `Set` of expanded root ids in `recipe/[id].tsx`, not server state); an edited comment shows "(modifié)" whenever `edited_at` is set, nothing more.
- **Navigation back to a comment is best-effort.** `profile.tsx`'s "Mes commentaires" cards push to `/recipe/{id}?tab=community&highlightComment={id}`; the recipe screen reads those as `useLocalSearchParams`, switches to the Communauté tab, expands the target's reply group if needed, and does an approximate `scrollTo` plus a ~2s highlight — there's no exact-position guarantee, and none was asked for.

### Production planning — `backend/production.py`, `backend/plans.py`

A production is a planned baking day: recipes + quantities, back-planned from a target time. Two modules sit outside `server.py`:

- `production.py` — **pure functions, no DB or network**, so they can be unit-tested directly (the rest of the suite is HTTP-only). `parse_duration` ("1 h 30" → 90), `parse_ingredient`, `scale_ingredients`, `aggregate_ingredients`, `compute_batches`, `build_steps`, `compute_schedule`, `summarize`. Two rules that look like bugs but aren't: **nothing is ever guessed** — a step with no stated duration stays undated and everything *upstream* of it stays undated too (reported in `missing_durations`); and ingredients are grouped on the exact normalized name, so `farine T65` and `farine T45` are deliberately **not** merged.
- `plans.py` — the Free/Pro limits (`PLAN_LIMITS`) and `resolve_plan`. Free = 3 productions/month. There is **no billing provider**: Pro is granted by the `PRO_EMAILS` env var (comma-separated). Enforcement is server-side in `_enforce_production_quota`, which raises a 403 carrying a structured `{"error": "plan_limit_reached", ...}` body so the app can open the Pro screen instead of showing an error.
- Productions **snapshot** the recipe's ingredients, steps and `yield_pieces` at creation, so editing a recipe never rewrites a planning already in use. `_carry_over_step_state` re-matches steps by `(recipe_id, order)` on update, preserving tick status and manually-entered durations.
- Recipes have an optional `yield_pieces` (pieces per batch). When it's absent, quantities fall back to "fournées" — never to an invented piece count.

### Swipe-to-act on Planning rows — `frontend/src/SwipeableRow.tsx`, `frontend/app/(tabs)/planning.tsx`

Both planning lists (Production and Personnel) already had a way to edit/delete a row: tap it, land on `production/[id].tsx` or `schedule/[id].tsx`, use the pencil icon / "Supprimer" button there. Swiping a row left reveals `Modifier`/`Supprimer` directly on the list as a *second* way to reach those same actions — never a second implementation of them.

- **`SwipeableRow` wraps `react-native-gesture-handler/ReanimatedSwipeable`**, not a new dependency: both `react-native-gesture-handler` and `react-native-reanimated` were already installed and the whole app is already wrapped in `GestureHandlerRootView` (`app/_layout.tsx`). The deprecated class-based `Swipeable` export was deliberately avoided in favour of the Reanimated one the library itself points to.
- **`onEdit`/`onDelete` are always the caller's existing handlers.** In `planning.tsx`, swiping a production row's `Modifier` pushes to `/production/new?id=...` — the exact route `production/[id].tsx`'s own pencil icon already uses — and `Supprimer` calls `confirmAsync('Supprimer cette production', 'Cette action est définitive.', 'Supprimer', true)` then `DELETE /productions/{id}`, byte-for-byte the same call `production/[id].tsx`'s `confirmDelete` makes (down to the live-activity/widget sync calls), just followed by `load()` to refresh the list in place instead of `router.replace`. The Personnel side mirrors `schedule/[id].tsx`'s `confirmDelete` the same way, and `Modifier` pushes to `/schedule/{id}` — that screen doubles as its own editor (`isNew = !id || id === 'new'`), so there is no separate edit route to reuse.
- **One row open at a time, tap-elsewhere-closes.** `planning.tsx` keeps one `openRowId` ref and a `Map` of stable `RefObject`s (one per row, keyed by id — `ReanimatedSwipeable`'s `ref` prop only accepts a `RefObject`, not a callback ref). Opening a row closes whatever was open (`onSwipeableWillOpen`); tapping *any* row's `Pressable` while one is open closes it and swallows that tap instead of navigating (the Mail-app convention) — only when nothing is open does the tap behave exactly as it always did. Swiping back right to close is `Swipeable`'s native behaviour, not custom code.
- **Action order matches the mockup, not the library's default.** `renderRightActions` renders `Supprimer` before `Modifier` in JSX because the panel's container is `flexDirection: row-reverse`: the first child lands at the outer edge, the second stays adjacent to the row content — so visually `Modifier` reads first (closer to the content) and `Supprimer` last (at the screen edge), left-to-right, as specified.
- Vertical scroll inside the `ScrollView` and the horizontal pan gesture were never made to cooperate by hand — `PanGestureHandler`'s built-in axis negotiation is what `Swipeable` already relies on; no extra config was needed or added.

### iOS home-screen widget + Live Activity — `frontend/targets/widget/`, `frontend/modules/bakers-live-activity/`, `frontend/src/widgetData.ts`

A real WidgetKit extension (not a React Native component that looks like one), showing today's production on the iPhone home screen, lock screen, and — while a step is being baked — as a Live Activity. Built on top of the exact same production data and endpoints `planning.tsx`/`production/[id].tsx` already use; no parallel data model, no new backend route.

- **The app was, until this feature, a pure managed Expo project**: no `ios/`/`android/` directories were ever checked in (confirmed empty before this work), no native customization beyond config-plugin strings (`expo-notifications`, `expo-media-library`, `expo-splash-screen`), no App Group, no entitlements. `ios/`/`android/` stay that way — regenerated by `expo prebuild`/EAS Build (`.gitignore`), never committed. The widget and its Xcode target live entirely as **source**, under `frontend/targets/widget/` (Swift) and `frontend/modules/bakers-live-activity/` (a local Expo Module), both of which *are* committed.
- **Config plugin**: [`@bacons/apple-targets`](https://github.com/EvanBacon/expo-apple-targets) generates the widget's Xcode target at prebuild time from `targets/widget/expo-target.config.js` — chosen over a hand-written config plugin because mutating an Xcode project file correctly by hand is exactly the kind of thing that's easy to get subtly wrong, and this plugin is purpose-built for adding native Apple targets (widgets, Live Activities, share extensions…) to a managed Expo app without ejecting. It also ships `ExtensionStorage`, the native module `src/widgetData.ts` uses to write into the shared App Group storage and to trigger `WidgetCenter.reloadAllTimelines()` — there was no need to hand-roll that bridge.
- **App Group**: `group.com.lucasmorey.bakers`, declared once in `app.json` (`ios.entitlements`) and mirrored in `targets/widget/expo-target.config.js` (`config.ios.entitlements[...]`, never duplicated as a literal string in two places). Verified by running `npx expo prebuild --platform ios --no-install` in this environment (no Xcode available here) and inspecting the generated `.entitlements` files and `.pbxproj` — the entitlement, the `widget.appex` app-extension target, its bundle id (`com.lucasmorey.bakers.widget`), and its auto-generated `Info.plist` (`NSExtensionPointIdentifier: com.apple.widgetkit-extension`, which hosts both the widget and the Live Activity) all came out exactly as configured.
- **Data contract, never a separate model**: `src/widgetData.ts`'s `buildWidgetSnapshot()` reuses the *exact* time and quantity rules `production/[id].tsx` already applies — a line's displayed time is the earliest known `start_at`/`end_at` among its steps (same "anchor" logic, copied not reinvented), and its quantity label is `{quantity} pièces` (pieces mode), `{batches × yield_pieces} pièces` (batches mode with a yield), or `{batches} fournées` (batches mode without one) — never an invented piece count. A line whose steps are all undated shows no time rather than a guessed one. `WidgetSnapshot.swift` is a hand-kept mirror of the TS type for `JSONDecoder` on the widget side; if the JS shape changes, update both in the same commit.
- **Sync points, all reusing existing mutations**: `syncWidgetData(userId)` is called after `POST/PUT/DELETE /productions` and after a step `PATCH` (`production/new.tsx`, `production/[id].tsx`), once after login/register and once at app-launch token restore (`auth.tsx`), unconditionally — it always re-fetches "today" fresh from the server, so editing a production dated some other day is a harmless no-op for the widget rather than something each call site has to reason about. **Logout calls `clearWidgetData()` before the token is even cleared** — `{"logged_in": false}` is written and the widget reloaded first, closing the window where a second account on the same device could otherwise see the previous one's production.
- **Refresh policy is native, not polled**: the widget's `TimelineProvider` asks iOS to reload at whichever comes first — the next local midnight (a new production day, never yesterday's shown stale) or a 45-minute check-in — and otherwise does nothing; there is no loop, and iOS itself throttles actual reload frequency by engagement. The app-triggered `reloadWidget()` calls above are what make an edit show up promptly in practice.
- **States, never fictional**: logged out → "Connectez-vous pour afficher votre production" (taps to `bakers://auth`); logged in with nothing scheduled → "Aucune production prévue aujourd'hui"; a read/decode failure on the widget's side simply falls back to whatever was last written, or the empty state — never a crash, never a fabricated number.
- **Deep links reuse Expo Router as-is**: `bakers://production/{id}` and `bakers://auth` need zero extra linking configuration — Expo Router maps a custom scheme onto the file-based route tree automatically, so `bakers://production/{id}` already opens `app/production/[id].tsx` with `id` filled in. The widget always links to a concrete production id it already has from its own snapshot, deliberately never a symbolic `.../today`, since no such route exists (nor should one). Small widget: the whole tile is one `widgetURL`. Medium/large: one `Link` per row — WidgetKit has supported multiple per-row `Link`s for plain navigation since iOS 14; that's not an iOS-17-only capability, only *interactive* (`Button`/`AppIntent`) widget content is.
- **Design**: the app has **no dark palette today** (`theme.ts` is a single flat color set; `useColorScheme`/`Appearance` are used nowhere in the app). So the widget doesn't try to mirror a dark theme that doesn't exist — it uses iOS's own dynamic system colors for background/text (`Color(.systemBackground)`, `.primary`, `.secondary`), which adapt automatically, and reserves the one fixed brand hex (`#C05A35`, `theme.color.brand`) for accents (icons, the `$accent` asset catalog color, Live Activity chrome). System font rather than the app's editorial serif (`Georgia`): at widget scale, legibility wins over stylistic fidelity, and the brand color alone carries the identity.
- **Lock screen families** (`accessoryRectangular`, `accessoryInline`) share the same `TimelineProvider` and data — no separate sync path, no separate deployment-target bump for the main app (an extension target can declare a higher `deploymentTarget` — `16.1` here — than the app that hosts it).
- **Live Activity ("cuisson en cours") is minimal and entirely local** — no push token, no background updates, exactly like the existing cooking timers (`TimerContext.tsx`, already 100% local). `BakeryActivityAttributes` lives once, in `targets/widget/_shared/`, linked by the plugin into *both* the app target and the widget extension (Apple requires the same type on both sides) — never duplicated. `modules/bakers-live-activity/` is a small local Expo Module (native Swift, no JS npm package, autolinked automatically because it lives under `frontend/modules/`) exposing `start`/`update`/`end`; `production/[id].tsx`'s single step-status choke point (`patchStep`) calls it: a step going to `"doing"` starts the activity (or updates it, if one is already running for that step and only its duration changed via the duration field), one leaving `"doing"` ends it. The countdown shown is computed the same way the existing "start timer" feature already computes one (`duration_minutes` from now), not the production's original back-planned `end_at`, so the Live Activity and the in-app timer never disagree.
- **What's verified here vs. what needs Lucas's Mac**: this sandbox has no macOS/Xcode. Verified in this environment: `tsc --noEmit`, `yarn lint` (no new issues), the full backend suite (untouched, so unsurprisingly green), and `npx expo prebuild --platform ios --no-install` succeeding with the App Group/entitlements/target/Info.plist all correct. **Not verified here, and blocking until done on a Mac**: `ios.appleTeamId` is not set in `app.json` (prebuild warns about it — Lucas's Apple Team ID from Xcode's Signing & Capabilities tab needs to go there); an **App Group requires a paid Apple Developer Program membership**, not a free personal-team account; actually compiling the widget/Live Activity Swift, running it on a simulator/device, adding the widget to a home screen, checking both color schemes by eye, the full account-switch/offline/restart matrix, and a real `eas build --profile preview` through TestFlight.

### Staff schedules — `backend/staff.py`, `frontend/src/schedule/`

A weekly grid of up to 15 people, Sunday to Saturday, with automatic hour totals. It lives under the **Planning** tab (a `Production` / `Personnel` segment), not a seventh tab.

- `staff.py` — pure functions, like `production.py`. Everything is counted in **minutes** and only formatted at the edges, so totals stay exact. A shift whose end is before its start has crossed midnight (`22:00 → 6:00` is 8 h). An empty cell, a day off and an unreadable time are three distinct states and stay distinguishable — an invalid time is rejected at the API rather than silently counted as zero.
- **Overtime is typed in by hand**, never derived: Baker is not told what a normal week is, and a guessed threshold would produce figures a manager could not justify. `total = worked + overtime`.
- Weeks must start on a Sunday (`_validate_week_start`), which is what makes the printed grid line up. `POST /api/schedules/{id}/duplicate` copies a week onto another one; the note is deliberately *not* copied, since it describes its own week.
- **Two export layouts, on purpose** (`frontend/src/schedule/`): `ExportLayout.tsx` is captured by `react-native-view-shot` into a PNG for Photos and sharing, at a fixed 1400 px so the result never depends on screen size; `printHtml.ts` builds A4-landscape HTML for `expo-print`, because a 15-row table rasterised at phone resolution is unreadable on paper. Both are black-on-white rather than themed, and carry no app chrome. User text is escaped in the HTML (`escapeHtml`).
- `export.ts` holds all three actions and never throws into the render tree — each returns `{ok, message}`. Photos is native-only, so the web build says so plainly instead of failing silently; a permanently denied permission offers Settings rather than a pointless retry.
- Exports always run against the **saved** schedule, so an image can never show figures the server has not computed. The buttons are disabled while there are unsaved edits.

### Advertising — `backend/plans.py` (`ads_config`), `frontend/src/ads/`

Ads are **built but switched off**. The architecture is complete; no ad SDK is installed and nothing renders.

- **The server decides.** `ads_config(plan)` in `plans.py` is the only authority: `ADS_ENABLED` (a master switch, default off) AND `plan == "free"`. `/api/me/plan` returns it under `ads`. A client bug therefore cannot show an ad to a Pro account. `available` reports the global switch regardless of plan, so the Pro screen only promises "no ads" when ads actually exist.
- **`frontend/src/ads/`** is the whole client side. `provider.ts` holds the `AdProvider` contract and the current `noopProvider` — swapping in AdMob means writing one object and changing one export, with no screen changes (the file carries the step-by-step instructions). `AdsContext.tsx` fetches the plan once at the root and exposes `canShowAds`. `AdSlot.tsx` is the only component screens use; it renders `null` (never an empty box) when ads aren't allowed, behind an error boundary so a misbehaving ad can't take a screen down. `layout.ts` decides where slots fall in a list.
- **Fails closed.** `canShowAds` requires the plan to be *loaded*, the server to allow it, and consent to be `granted`. Any failure — offline, server error, no consent flow — lands on "no ads".
- Placements: one slot on the home screen between sections, and inline in the recipe list (after the 6th card, then every 10 — tunable via `ADS_LIST_FIRST_SLOT`/`ADS_LIST_INTERVAL` without an app release). Deliberately **none** on recipe detail, planning, chat, calculator or the share form, and **no interstitials at all**.
- Do not turn `ADS_ENABLED` on until (a) Baker Pro is actually purchasable and (b) `provider.ts` implements the Google UMP consent flow plus iOS ATT — users are in the EEA and AdMob suspends accounts that request ads before a certified consent form has run.

### Message photos — `backend/moderation.py`, `backend/imaging.py`, `frontend/src/revealedPhotos.ts`

A message can carry a photo. The rule the whole feature is built around: a photo flagged as potentially sexual is never blocked — it sends normally, but the recipient sees it blurred behind a warning until they choose to reveal it. Only a photo scored as unambiguously explicit is refused outright, before anything is stored.

- **Detection**: Sightengine's classic `nudity` model (`raw`/`partial`/`safe` scores), chosen over Google Cloud Vision SafeSearch and AWS Rekognition specifically because it needs only a lightweight API user/secret pair — no cloud console, no billing account, no IAM — the same onboarding shape as `PEXELS_API_KEY`. Its free tier (2,000 checks/month) covers a friends-only messaging feature; see `backend/moderation.py`'s docstring for the full comparison and for why the classic model was used over the newer `nudity-2.1` (its field names are stable and well-documented; `nudity-2.1`'s were not verifiable against a live call from this environment's network policy at the time this was written).
- `moderation.classify(raw, partial)` is pure: only `raw` (fully explicit) can reach `blocked`; `partial` (partial nudity) can only ever push a photo to `sensitive`, never to `blocked` — potential nudity alone is never treated as forbidden. Both thresholds (`MODERATION_SENSITIVE_THRESHOLD`, `MODERATION_BLOCK_THRESHOLD`) are read from the environment, so they're retunable without a rebuild.
- **Fails cautious, not open.** If Sightengine is unreachable, unconfigured, or errors, `moderation.analyze()` never raises and never assumes a photo is safe — it returns the configured `MODERATION_FALLBACK` level (default `sensitive`). Running with no Sightengine credentials at all is therefore deploy-safe: every photo just stays blurred-by-default until real credentials are added.
- `MODERATION_PROVIDER=stub` swaps in a deterministic, network-free classifier keyed to a test image's average colour (red → blocked, orange → sensitive, blue → simulated outage, anything else → normal) — **test/local-dev only, never set in production**. This is what `test_messaging_photos.py::TestGraduatedLevels` needs to exercise all four outcomes without live credentials (see Commands above).
- **Images never leave the server larger than what gets shown.** `imaging.prepare_display()` resizes/compresses the upload before it is analyzed, stored, or shown (`MAX_DISPLAY_DIM`, 1600px). For a `sensitive` result, `imaging.make_blur_preview()` additionally produces a second artifact: the source is shrunk to `BLUR_SOURCE_DIM` (24px) *before* blurring, then scaled back up — detail is actually discarded, not just visually smeared, so the preview is safe to send before the recipient reveals anything, and the client never has to fetch the full photo just to render the blurred stand-in.
- **Private storage, not the public upload path.** Message photos are never written under `backend/uploads/` (served publicly, with no auth, by `GET /files/{path}`). They live in a separate `backend/private_uploads/` tree, reachable only through `GET /messages/photos/{message_id}`, which checks the requester is one of the message's two parties *and* is still friends with the other — same rule `GET /messages/{friend_id}` already enforces for text history. Two separate directory roots, not a prefix filter on a shared one, so a bug in the authorization check can never expose a private photo through the public route by construction.
- A `blocked` photo is refused at `POST /messages/{friend_id}/photo` (422) before `put_private_object` is ever called — nothing is written, nothing is sent, nothing is analyzed by anything downstream of that response.
- Reporting: `POST /messages/{message_id}/report` (reason: `sexual`/`illegal`/`violence`/`harassment`/`spam`/`other`) is new — no report system existed before this. Scoped to any message (not just photos) since the check (must be a party to the message) is identical either way, though only photo bubbles expose the report action in the UI today.
- Frontend: `src/revealedPhotos.ts` is a small AsyncStorage-backed set of revealed message ids (capped at 500, oldest dropped first) — "remember the choice" is a local preference, not a change to the message model. The sender always sees their own photo unblurred; only the recipient of a `sensitive` photo they haven't revealed yet sees the blur+warning overlay.

### Text moderation — `backend/text_moderation.py`

Recipe submissions (`POST /recipes`) and comments (`POST /recipes/{id}/comments`) are checked against a context-aware moderation model before being stored. Scope is deliberately just those two: messages are covered separately by `moderation.py` (image only, text out of scope there), and personal notes are never seen by anyone else. The problem this exists to solve: a generic banned-word filter would flag French baking vocabulary — "bâtard" is first and foremost a bread shape, not an insult — as forbidden. So a professional whitelist always wins over a ban-word match, not the other way around.

- Pure module, same family as `production.py`/`staff.py`/`moderation.py` — no DB, no network. `WHITELIST_TERMS` maps a normalized professional term (accents/case stripped via `production.normalize_name`, reused rather than duplicated) to either `None` (never has an insulting sense at all — "fougasse", "miche"…) or a list of context markers ("pain", "façonner", "levain"…) whose presence *anywhere in the same submitted text* confirms professional usage. `BAN_WORDS` is the operator-supplied list of forbidden terms, given by Lucas — not invented here. Entries can be a single word or a multi-word phrase ("nique ta mère", "trou du cul"…); both are matched as a contiguous, in-order run of normalized tokens against the submitted text (`_contains_phrase`), never as a naive substring or a simple word-set intersection — a set intersection alone would silently never catch a multi-word phrase.
- Three-tier decision, in priority order: **SAFE** (no ban-word hit, or a ban word whose whitelist entry is `None` or whose context marker is found elsewhere in the text) → publishes normally. **REVIEW** (a whitelisted term matched with no context marker anywhere — genuinely ambiguous) → **still publishes normally**, never auto-blocked on ambiguity alone, but is logged to a new `flagged_content` collection for later manual review — there's no admin UI, it's a log to query directly. **BLOCKED** (a ban word with no whitelist entry at all — no professional sense to save it) → rejected with a generic 422 before anything is inserted; the response never names the matched term, so the message can't be reverse-engineered into a filter-bypass guide.
- `_moderate_and_flag()` in `server.py` is the single call site both `create_recipe` and `add_comment` go through, right after building the document and before `insert_one`. `classify_recipe(title, description, ingredients, steps)` searches for context across *all* of a recipe's fields, not just the one the term appeared in — a title like "Bâtard de campagne" is legitimized by "façonner" showing up in the steps.
- **Never remove "bâtard" from the terms this module watches without thinking about context first.** It must stay an explicit `WHITELIST_TERMS` entry (not just absent from `BAN_WORDS`) so the system always knows it's a legitimate professional term in this app, however the ban list evolves. Two entries were added the same way after the fact: "gueule" ("la gueule du four", the oven's opening) and "gerbe" ("une gerbe de blé", a bread decoration) are both real professional terms *and* words Lucas's ban list includes — check any new `BAN_WORDS` addition against the seeded catalogue and against real trade vocabulary before assuming it's safe to leave unwhitelisted; `tests/test_text_moderation_calc.py::TestRealBanWordsList` runs `classify_recipe` over ordinary recipe text against the live `BAN_WORDS` as a regression net for this.
- `TEXT_MODERATION_TEST_BAN_WORDS` (env var, comma-separated) merges extra test-only words into `BAN_WORDS` at import — same idea as `MODERATION_PROVIDER=stub` above. **Test/dev only, never set in production.** It's what lets `tests/test_recipe_moderation.py::TestBlockedAndReview` exercise the real BLOCKED/REVIEW paths of a running server without asserting on Lucas's real list directly; those tests skip themselves when it's unset (set `TEXT_MODERATION_TEST_BAN_WORD_FOR_TESTS` to the same word so the test file knows what to assert against).

### Frontend — `frontend/`

Expo Router (file-based routing) under `app/`:

- `app/_layout.tsx` — root: wraps everything in `AuthProvider` (`src/auth.tsx`), `AdsProvider` (`src/ads/`) and `TimerProvider` (`src/TimerContext.tsx`), renders the global floating `TimerBar`.
- `app/(tabs)/_layout.tsx` — the tab group (`Accueil`, `Recettes`, `Assistant`, `Amis`, `Profil`); redirects to `/auth` if `useAuth().user` is null. This is the entire route-protection mechanism — there's no per-screen guard.
- `app/auth.tsx`, `app/recipe/[id].tsx`, `app/baker/[id].tsx`, `app/chat/[id].tsx`, `app/calculator.tsx`, `app/share.tsx` — stack screens outside the tab group.

Cross-cutting modules in `src/`:

- `src/api.ts` — the only place that talks to the backend. `api(path, opts)` wraps `fetch`, injects the bearer token from `expo-secure-store` (web falls back to `localStorage`), and throws on non-2xx. All screens call through this rather than `fetch` directly.
- `src/auth.tsx` — `AuthProvider`/`useAuth()`; on mount, checks for a stored token and validates it against `/api/auth/me`.
- `src/TimerContext.tsx` — global baking timer state (single timer or a chained multi-step sequence), independent of whichever screen started it, backed by `expo-notifications` for background alerts. `recipe/[id].tsx` parses step text for durations (`parseDuration`) to auto-offer timers.
- `src/theme.ts` — the single source of design tokens (colors, spacing, radius, font sizes) consumed by every screen's `StyleSheet`. `design_guidelines.json` at the repo root is the original aspirational design brief and doesn't fully match the shipped theme (e.g. it specifies Cormorant Garamond/Geist; `theme.ts` actually uses Georgia/system-serif) — treat `theme.ts` as ground truth.

There's no data-fetching library (no React Query/SWR): each screen does its own `useEffect` + `useState` + manual loading/error state, calling `api()` directly.

## Gotchas

- `.emergent/`, `design_guidelines.json`, and `frontend/constants/testIds/` are leftovers from the app's original AI-scaffolded build (the "Emergent" platform) and from an unused automated-QA pipeline (`testIds/auth.js` is never imported anywhere). Harmless, safe to ignore or remove — just don't mistake them for live infrastructure.
- `frontend/scripts/cmd-guard.js` runs on `yarn`'s `preinstall` hook and blocks a handful of deprecated Expo packages (`expo-av`, `expo-barcode-scanner`, `expo-background-fetch`, `expo-file-system/legacy`). It no-ops for everything else outside its original sandbox (falls back to a small baked-in rule list) — if `yarn add`/`yarn install` ever fails with a "cmd-guard: Blocked" message, it's this script, not a real dependency conflict.
- Root `.gitignore` has `.env.*` (blocks committing local secrets) with an explicit `!.env.example` exception — keep that pairing if you add new env-var scaffolding.
